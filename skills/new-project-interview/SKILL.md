# new-project-interview

Guided interview for new project setup decisions. One question at a time, like grill-with-docs.

<workflow>

1. **Explore project context** — if in an existing repo, read files to understand the scenario. Otherwise, ask the project name/idea.
2. **Walk through 6 phases** — one question at a time, wait for answer, document each decision in `docs/setup/decisions.md`
3. **Generate final document** — at the end, save the complete decisions.md

</workflow>

## Core rules

- **ONE question per message.** Do not ask 2 questions together. If a topic needs exploration, split into multiple questions.
- **Always offer your recommendation** with pros/cons. Don't drop the decision in the user's lap without guidance.
- **Document each decision immediately** after the user responds. Don't wait until the end.
- **Sharpen fuzzy language** — if the user says "I want a simple system", ask what "simple" means to them. If they say "I want a SaaS", ask what problem it solves.
- **Flag contradictions** — if current decision conflicts with a previous one, warn them.
- **Context-aware recommendations** — the recommendation should account for previous decisions (e.g., if the purpose is learning, recommend new technologies; if it's making money, recommend what the user already knows).
- **If the user is in an existing project**, use the code to infer already-made decisions — don't ask the obvious.

## The 6 phases

### 1. Purpose — understand the goal

Ask (1 per turn):
- What is the main goal? Learning vs making money? Personal project vs client?
- Are you solo or do you have a team?
- Is there a deadline? Monthly budget for infra?
- What stack do you already know?

### 2. Stack — choose technologies

Based on purpose, offer 2-3 options with pros/cons. Typical paths:

**Focus on fast delivery (making money):**
- NextJS (fullstack JS, SSR, ecosystem) — _recommended if you already know JS_
- Django + template (Python, batteries-included, native admin)
- Laravel (PHP, batteries-included, great for CRUD)

**Focus on learning:**
- Elixir/Phoenix (concurrency, fault-tolerance)
- Go + HTMX (simplicity, performance)
- Rust + Axum (maximum performance, type system)

**DB:** PostgreSQL (recommended default) vs SQLite (quick prototype) vs MySQL (legacy)
**ORM:** Drizzle (JS/TS, lightweight, type-safe) vs Prisma (JS/TS, productive) vs Django ORM vs SQLAlchemy

If the user already declared purpose "making money" and stack "JS", recommend NextJS + Drizzle + PostgreSQL.

### 3. MVP — model the minimum

- What is the system's main entity? (User? Product? Project? Order?)
- What is the minimum that needs to work to be useful?
- Do you need auth from the start? (recommend yes, and choose a provider)
- Suggested folder structure: `/app`, `/components`, `/lib`, `/db`, `/tests`

### 4. Deploy — infrastructure

- Where to host? National VPS (HostGator, Locaweb) vs international (Railway, Vercel, Fly.io)?
  - If Brazilian audience: VPS in SP (lower latency). Recommend HostGator or similar.
  - If global audience: Railway/Vercel more practical.
- CI/CD: GitHub Actions (default, recommended)
- Need Docker? (recommend yes for VPS, no for Vercel/Railway)
- Custom domain? (recommend yes)

### 5. Testing — quality

- Appropriate amount of testing for the moment? Unit + integration enough?
  - If fast MVP: unit tests only on critical parts
  - If serious product: CI with mandatory tests before merge
- Framework: Vitest (JS) or pytest (Python) — recommended
- E2E only later if needed
- Minimum coverage? (don't enforce at start, but set up tooling)

### 6. DX — documentation and conventions

- README: how to install, run, test, deploy
- AGENTS.md: instructions for AI (TDD? typing conventions? how to run tests? architecture?)
- Linter/formatter? (ESLint + Prettier / Ruff)
- Commit conventions? (Conventional Commits — recommended)

## Output: decisions.md

Create/update `docs/setup/decisions.md` with each decision. Format:

```markdown
# Setup Decisions: [Project Name]

> Generated by new-project-interview — [date]

## 1. Purpose
- **Goal:** [learning | making money | both]
- **Team size:** [solo | team of N]
- **Deadline:** [description]
- **Budget:** [description]
- **Known stack:** [technologies you already know]

## 2. Stack
- **Frontend:** [technology] — [brief justification]
- **Backend:** [technology] — [brief justification]
- **Database:** [technology] — [brief justification]
- **ORM:** [technology] — [brief justification]

## 3. MVP
- **Core entities:** [main entities]
- **Minimum features:** [essential features]
- **Auth:** [yes/no + provider]
- **Folder structure:** [description or template]

## 4. Deploy
- **Hosting:** [VPS | PaaS | Serverless + which]
- **CI/CD:** [GitHub Actions | other]
- **Docker:** [yes/no]
- **Domain:** [yes/no + which]

## 5. Testing
- **Types:** [unit | integration | e2e]
- **Framework:** [which]
- **CI pipeline:** [run before merge?]
- **Coverage:** [enforce or just setup]

## 6. DX
- **AGENTS.md:** [yes/no + main content]
- **Linter:** [which]
- **Commits:** [conventional | free]
- **README:** [basic instructions]
```

## Phase transition

After documenting the current phase decision, say something like:

> "Noted. Next phase: **[phase name]**. [1-line explanation of what we'll decide]"

If the user wants to skip a phase or go back, allow it. Don't force order.

## When NOT to use this skill

- Project already in progress with written code (use brainstorming or another skill)
- Just a specific question about a technology (answer directly, no interview)
- The user has already made all decisions and just wants code generation (use writing-plans)
